# 文档体系

规范正文在 `references/doc-standard.md`，**先读它**。本文件只讲流程。

## 文档权限

- 可以读取全部项目文档和代码事实，不得把历史决策或当前状态猜成未确认需求。
- 可以维护 `AGENTS.md`、`README.md`、`DESIGN.md`、`PLAN.md`、`MEMORY.md`、`DECISIONS.md`、`CHANGELOG.md`。
- `REQUIREMENTS.md` 由用户决定内容。可以从用户原话或既有文档中提炼草稿，**经用户明确确认后**写入；不得发明、扩写或自行改变需求。
- 存量迁移时，先给用户看盘点和去向，得到确认后再改；只搬运，不借迁移改写需求。

## 第 0 步：判定项目类型

用硬判据，不靠感觉：

| 判据 | 结论 |
|---|---|
| 有构建或运行产物（exe / apk / dll / mod / 脚本入口 / 依赖清单） | **程序类** |
| 只有文本、图片、数据 | **内容类** |
| 两者都有 | **程序类**，并允许有内容目录 |

判定结果必须写进 `AGENTS.md` 第一行：`项目类型：程序类（含内容目录 Cards/）`。以后任何人（或 AI）都不用再猜。

模板：`assets/program-templates.md` / `assets/content-templates.md`。只读取当前项目类型对应的模板。

## 第 1 步：盘点，先看不动

1. 列出根目录与 `docs/` 下所有 `.md`、`.txt`
2. 每个文件归到 8 类之一，**归不进去的单独列出来**（那通常是临时草稿或历史记录）
3. 找出重复：同一事实出现在两个文件里的，**逐条记下来**（这是本次整改的主要收益）
4. 找出空文件与死链
5. 查 git：工作区是否干净、当前 HEAD 是什么、待删文件是否都被 HEAD 跟踪——这是后面「提炼后删除」的安全前提

盘点结果先给用户看，得到确认后再开始改。

## 第 2 步：只补缺的

- 程序类和内容类项目都建立完整 8 个文件；缺哪个建哪个，**不重写已有的**。
- 已有文件能承担新职责的，改名归位即可（用 `git mv` 保留可检测的历史）。
- 新建的空文件必须过「最少内容门槛」（见规范 §6）。

## 第 3 步：建立权威关系

- `AGENTS.md` 写文档导航表，每行标状态：`✅ 有效` / `⬜ 待填`
- `docs/` 各文件顶部写一行「本文档不含 X，X 见 Y」（X = 进度 / 需求 / 决策）
- 同一事实只留一处，其余改为链接

## 第 4 步：处理旧文档

按 `references/migration.md` 执行：**先提炼，再删除**。删除前必须逐个确认原文已被 HEAD 跟踪，或已有项目外备份；仅凭 `git status` 干净不够。

## 第 5 步：验收（可测，不靠感觉）

模拟「新会话接手」：只读 `AGENTS.md` + `docs/MEMORY.md` + `docs/PLAN.md`，能否答出

1. 现在做到哪一步、下一步做什么
2. 改代码不能违反哪些约束
3. 该去哪找需求、设计、决策

答不出 = 没写完，回去改对应权威文件，不要通过复制同一事实来补救。

## 禁止

- 未经用户明确确认写入或改写 `REQUIREMENTS.md`；只能提炼用户原话和已确认结论，歧义必须问
- 发明业务内容（数值、规则、流程）
- 把同一事实写两处（即使「复制一份方便看」也不行）
- 建了空文件却不写「为什么还是空的」
- 一次性改造多个项目（先跑通一个，规范大概率还要改）
- 自动 commit、stash 或删除文件；这些动作必须另有用户明确授权

## 判断「该不该建额外文件」

完整 8 个文件是固定基线。额外文件值得存在，当且仅当：**有人（或 AI）会在某个具体时刻专门去读它**。说不出「谁会读、什么时候读」，就不要建第 9 个文件。
