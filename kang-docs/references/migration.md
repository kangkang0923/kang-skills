# 存量项目改造步骤

适用：已经有文档但结构混乱的项目。**一次只做一个项目。**

## 0. 前置检查（缺一不可）

- [ ] 判定项目类型（程序类 / 内容类 / 混合），写下来
- [ ] `git status` 干净；不干净就停下并交给用户处理，**不自动 commit 或 stash**
- [ ] 记下当前 HEAD 提交号，供核对原文来源
- [ ] 项目没有 git 的：经用户确认备份位置后，先把要删的文件复制到项目外的备份目录

> `git status` 干净不等于文件可恢复：被忽略或从未跟踪的文件也可能不在 HEAD。删除前必须逐个验证。

## 1. 盘点（只看不改）

产出一张表，给用户过目：

| 现有文件 | 大小 | 归到哪一类 | 处理 |
|---|---|---|---|
| `README.md` | 9.9 KB | README + DESIGN + AGENTS 混合 | 拆分 |
| `docs/README.md` | 2.4 KB | 与根 README 重复 | 提炼后删除 |
| `docs/DESIGN.md` | 29.8 KB | 契约 + 进度混合 | §1~§11 留，§12~§15 抽走 |

同时在表里标出**同一事实出现在多处的清单** —— 这是整改的主要收益来源。

## 2. 提炼（写新文件，此时还不删）

按去向写：

| 旧内容 | 新家 |
|---|---|
| 目标、验收标准、明确不做的事 | `docs/REQUIREMENTS.md`（先展示提炼结果，经用户明确确认） |
| 架构、算法、不变量、数据结构 | `docs/DESIGN.md` |
| 当前状态、待实机项、临时环境问题 | `docs/MEMORY.md` |
| 未完成事项、下一步 | `docs/PLAN.md`（待办区） |
| 为什么这么定、被否方案 | `docs/DECISIONS.md` |
| 版本级变化 | 根目录 `CHANGELOG.md` |
| 构建/运行/发布命令、硬约束、长期有效的非直觉坑 | `AGENTS.md` |

提炼规则：
- **只搬不发明**。原文没有的事实不许补。
- 原文互相矛盾时，停下来问用户「以哪个为准」，不要自己选。
- 状态类（带日期、带「已确认/待验证」）优先归 `MEMORY.md`，不要留在 `DESIGN.md`。
- 同一内容只搬到权威文件；不要因为「接手时方便」再复制到其他文档。

## 3. 删除

- 内容已全部有去处，且用户已经检查并确认提炼结果，才进入删除步骤。
- 先列出精确待删清单。有 git 时，对每个文件执行 `git ls-files --error-unmatch -- <path>`；只有被当前 HEAD 跟踪的原文才可删。
- 未跟踪、被忽略、命令失败或无法确认可恢复的文件，**不得删除**；先交给用户处理。
- 无 git 时，先确认项目外备份真实存在且内容可读。
- 得到用户明确删除授权后用 `git rm`；普通文件使用删除工具，不用无法审查的批量通配删除。
- 删除后检查 diff 与 `git status`，确认没有误删、没有覆盖用户的其他改动。

## 4. 建导航

- `AGENTS.md` 的文档导航表：每行 `文件 | 内容 | 状态(✅/⬜)`
- 每个 `docs/` 文件顶部加一句「本文档不含 X，X 见 Y」
- `README.md` 只留「这是什么 / 怎么用起来 / 文档在哪」，其余提炼到权威文件后再删

## 5. 验收（可测）

开一个**全新会话**，只说「接着做 <项目名>」，检查：

1. 是否只读 `AGENTS.md`、`MEMORY.md`、`PLAN.md` 就能答出「现在做到哪、下一步做什么」
2. 是否没有被迫读完整份 `DESIGN.md`
3. 让它改一处代码，是否主动先声明硬约束
4. 问「为什么不用方案 X」，是否能从 `DECISIONS.md` 找到答案
5. 检查文档链接、空文件说明和导航状态是否有效

任何一条不过 → 回来改对应权威文件，不要继续铺下一个项目。

## 6. 提交

只有用户明确要求提交时才执行。一次提交只做「文档体系改造」一件事，提交信息写清：新增哪些、删除哪些、提炼自哪个文件；否则保留 diff 交给用户检查。

## 常见坑

- **别顺手改代码**。改动混在一起后无法回滚验证。
- **别改历史记录里的事实陈述**（「当时在 D:\AI 下操作」这类保留原样，改写会造成失真）。
- **别在改造中更新规范**。发现规范有问题，记在待定里，等这个项目做完再统一改。
- 旧文档里如果只有一处信息（无法从别处恢复），提炼时必须逐字搬，不要概括。
