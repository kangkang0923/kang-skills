# 项目文档规范

> 本文件是规范的**唯一正文**。工作区别处只放指针，不复制内容。
> 决策理由记录在各项目自己的 `docs/DECISIONS.md`；本文件不依赖本机绝对路径。

## 1. 这套规范解决什么

新会话接手时最常见的三件事：

1. 不知道「现在做到哪」，只能把几百行交接日志读一遍
2. 同一个事实散在三份文档里，互相矛盾
3. 已经否决过的方案，过两周又提出来一遍

对策只有一条原则：**同一事实只存一处，且每类事实有固定的家。**

## 2. 八个文件

| # | 文件 | 位置 | 作者 | 装什么 | 生命周期 | 谁能改 |
|---|---|---|---|---|---|---|
| 1 | `README.md` | 根 | AI 起草，用户确认定位与用法 | 这是什么、怎么快速用起来、文档入口 | 慢改 | AI 可维护，不擅自改变产品定位 |
| 2 | `AGENTS.md` | 根 | AI | 构建/验证命令、硬约束、长期有效的非直觉坑、文档导航 | 慢改 | AI 可维护；硬约束必须来自用户或已验证事实 |
| 3 | `REQUIREMENTS.md` | `docs/` | 用户决定，AI 可代写 | 要什么、不要什么、**验收标准** | 需求变了才改 | **AI 仅在用户明确确认后写入，不得发明需求** |
| 4 | `DESIGN.md` | `docs/` | AI | 实现契约、不变量、算法、数据结构 | 改结构要记 DECISIONS | AI |
| 5 | `PLAN.md` | `docs/` | AI | 待办、下一步 + 近期完成 | 打勾 + 压缩 | AI |
| 6 | `MEMORY.md` | `docs/` | AI | 当前状态、交接提示、临时环境问题 | **覆盖式** | AI |
| 7 | `DECISIONS.md` | `docs/` | AI | 为什么这么定、**被否方案** | **只追加** | 旧条目不修改；用新条目取代 |
| 8 | `CHANGELOG.md` | 根 | AI | 版本级变化 | 追加 | AI |

不用 `CLAUDE.md`（不用 Claude Code）。通用名用英文大写；项目特有文档可用中文名（如 `经济数值表.md`）。

## 3. 三份文件的分工

| | 回答什么 | 什么时候拿出来 |
|---|---|---|
| `REQUIREMENTS.md` | 要做什么、什么算做完 | 验收时对照 |
| `DESIGN.md` | 怎么做 | 编码前对照 |
| `DECISIONS.md` | 当初为什么这么定、为什么不那样 | 回头看、吵架时 |

口诀：**需求=验收时对照；设计=编码前对照；决策=回头时对照。**

## 4. 权威关系

```
REQUIREMENTS  >  DESIGN  >  MEMORY
```

- 冲突时优先级高的赢。
- `AGENTS.md` 是 AI 入口：包含命令、硬约束、长期有效的非直觉坑和文档导航，但**不复述** `docs/` 中已有的需求、设计、进度或决策理由。
- `DECISIONS.md` 是理由记录，不替代当前事实权威。若新决策改变设计，必须同步更新 `DESIGN.md`，并在新决策中写 `取代：D-xxx`；不得修改旧条目。
- `PLAN.md` 是任务与下一步的唯一权威；`MEMORY.md` 只写当前阶段与交接提示，下一步用链接指向 `PLAN.md`，不复制任务。
- `README.md` 不写当前状态，只链接 `MEMORY.md`。

## 5. 四条生命周期规则

### PLAN：打勾保留 + 分区 + 压缩

```
# PLAN

> 当前：<一句话，含日期>

## 待办
- [ ] ...

## 近期完成（保留最近 20 条，更早的已归档进 CHANGELOG）
- [x] ...
```

- 总长 **≤150 行**；超了就把最早一批压成一行主题汇总，全量移入 `CHANGELOG.md`
- 顶部「当前进度」一行必写
- **禁止**用行号游标让 AI「跳读前半段」：行号会随编辑漂移，必然失准。真正省成本的是文件体积

### MEMORY：覆盖式

永远只反映「现在」。旧状态不留 —— 要看历史去 git 或 `CHANGELOG`。
若允许追加，它会退化成第二份交接流水账（这是要避免的）。

### DECISIONS：只追加

格式：

```
### D-001 标题
- 结论：
- 理由：
- 被否方案：（没有就写「无」）
- 取代：（可选，填被本决策替代的 `D-xxx`；没有则省略本行）
- 日期：YYYY-MM-DD
```

- 新条目编号取当前最大编号加一，追加前重新检查，避免长会话使用旧编号。
- 允许杂：需求与设计已各有独立文件，这里就是对话决策的收纳箱。
- **不设**索引表、不设标签体系（会与实际条目不同步）；`### D-` 前缀足够用 grep 定位。
- 旧条目不修改；后来推翻它时新增条目并标 `取代：D-xxx`，同时更新当前事实权威文件。

### CHANGELOG：追加

- 固定放项目根目录。
- 程序类按版本小节（语义化版本）；内容类按月份小节。
- 只写「加了什么主题 / 改了什么 / 删了什么」，**不写具体条目**。
- 粒度 = 一次主题性改动。

## 6. 三出口规则（「已完成」往哪记）

`PLAN.md` 里的一行在消失或归档前，必须落到三处之一：

| 情况 | 落到哪 |
|---|---|
| 影响用户能感知的行为 | 写一句进 `CHANGELOG.md`，然后从 PLAN 移除 |
| 影响后续方案取舍（含被否方案） | 写成一条 `DECISIONS.md` |
| 两者都不影响（改措辞、修笔误） | 直接删，git 兜底 |

长期有效、改代码前必须知道的坑进 `AGENTS.md`；仅影响当前交接的临时问题留在 `MEMORY.md`。不要把它们再复制进 `DECISIONS.md`。

**记结论，不记操作。** 判据一句话：**「半年后的我，或下一个 AI，需要它吗」**。
「当时点了哪个按钮」永远不需要；「为什么不用 NotifyIcon」的取舍理由需要。

## 7. 最少内容门槛

允许建空文件（内容型项目也一样全套），但每个空文件必须写：

```
> 本文件暂无内容。原因：<一句话>。最后确认：YYYY-MM-DD
```

且 `AGENTS.md` 的导航表里标 `⬜ 待填`。**文件存在 ≠ 已完成。**

## 8. context 预算

AI 每次会话都会读入口文件，所以有硬上限：

| 文件 | 上限 | 超了怎么办 |
|---|---|---|
| `AGENTS.md` | 100 行 | 只有「命令、硬约束、非直觉的坑、导航」值得留，其余移入 `docs/` |
| `PLAN.md` | 150 行 | 压缩已完成区 |
| `README.md` | 150 行 / 约 3 KB | 细节移入 `docs/DESIGN.md` 或 `docs/` |
| `MEMORY.md` | 120 行 | 删掉已不是「现在」的内容 |
| `REQUIREMENTS.md` | 无上限 | 但每条都要能验收 |
| `DESIGN.md` | 无上限 | 不含进度 |
| `DECISIONS.md` | 无上限 | 靠 grep 定位，不必通读 |

判断标准：**一个只读入口文件的 AI，能不能在 3 次读取内定位到有效信息。**

## 9. 反模式

| 反模式 | 为什么坏 |
|---|---|
| 根目录放临时/草稿 md | 会沉淀成 0 字节空文件，且没人知道该不该读 |
| 空壳文档没有说明 | 制造「已完成」的错觉 |
| 同一事实写两处 | 必然漂移，AI 会引用较旧的那份 |
| 逐条操作流水账 | 关键状态被埋在几十轮细节里，越长越没人读 |
| 一个项目两份索引 | 两份都会过期，用户不知道该信哪个 |
| 用日期做文件名前缀（`2026-10-08-xxx.md`） | 目录会变成时间线，不是主题 |
| 把理由抄进 `DESIGN.md` | 理由只归 `DECISIONS.md`，两处必漂移 |

## 10. 项目类型

| 类型 | 判据 | 差异 |
|---|---|---|
| 程序类 | 有构建或运行产物（exe/apk/dll/mod/脚本入口/依赖清单） | 全套 8 个文件；`AGENTS.md` 含命令 |
| 内容类 | 只有文本、图片、数据 | 全套 8 个文件；`AGENTS.md` 写文件命名与禁止改动的规则；`DESIGN.md` 写内容组织方式；`CHANGELOG` 按月份 |
| 混合 | 两者都有 | 按程序类，并在 `AGENTS.md` 注明内容目录范围 |

判定结果写在 `AGENTS.md` 第一行。

## 11. 存量项目改造

见 `migration.md`。核心顺序：**盘点 → 建新/提炼 → 用户确认 → 验证可恢复后删除 → 改导航 → 验收**，且每次只做一个项目。
