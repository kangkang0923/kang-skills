# 拍板

## 什么时候用

- **用**：有 2 个以上可选方案，且选错的返工成本明显（换语言、换框架、换存储、单机还是联网、要不要后端）。
- **不用**：纯偏好（文件叫什么名、按钮放左放右）、已有明确指定、或需求还没定（先转 `kang-grill`）。

## 输入：区分需求与事实

**需求权威只有两个来源：**

1. 项目 `docs/REQUIREMENTS.md` 的目标、约束与验收标准
2. 本次对话里用户明确确认的结论

可以读取 `DECISIONS.md` 了解已否决方案，读取代码、依赖清单、`AGENTS.md` 和其他文档了解现状，但**禁止从这些材料猜出用户尚未确认的需求**。需求缺失或矛盾就先问，不在本 skill 中补写 `REQUIREMENTS.md`。

事实证据可以且应该来自代码、环境检查、软件包元数据和官方文档，不受上述两个需求来源限制。

## 文档权限

- 可以读取全部项目文档、代码和环境事实。
- 用户确认选型后，只更新下述 `DECISIONS.md`、`DESIGN.md`、`PLAN.md` 中的相关内容。
- 不改 `REQUIREMENTS.md`、`README.md`、`AGENTS.md`、`MEMORY.md`、`CHANGELOG.md`，也不修改实现文件。

## 步骤

### 1. 逐条比对清单

读 `references/questionnaire.md`：**6 条必答 + 6 条条件触发**。缺哪条问哪条，条件未命中的不问；能自己查到的环境事实不问用户。

- 每轮最多 5 条，且同轮问题之间不得有先后依赖。条件是否触发依赖未答问题时，留到下一轮。
- 每条附 `➡️ 建议：推荐答案 + 一句话理由`。
- 用户答「不知道 / 无所谓」时，给出具体默认值并说明后果，请用户确认，不要留空。

### 2. 验证事实，不靠记忆

- 版本号、许可证、平台可用性优先查官方页面或官方包元数据，附链接并注明「截至 <日期>」；查不到就写「需你核实」。
- **不许凭记忆写具体数字**（价格、免费额度、API 等级）。
- 涉及本机环境（已装 JDK/SDK/.NET/Node、能联网、有没有真机）时**先查再说**。

### 3. 比较实际可行的方案，按 boring technology 排序

通常给 2~3 套；调查后只有一套可行时只给一套，不为凑数虚构陪跑方案。第一套优先放「用户管得过来的最简单方案」。每套固定四栏：

```
### 方案 A：<一句话名字>
- 技术栈：（版本号只在影响选型且已核实时填写）
- 为什么适合：（对着需求里哪条约束）
- 维护成本 / 你得自己管什么：（密钥、权限、要打补丁的服务器；没有就写「无」）
- 主要风险：
```

只有**落选**的方案额外加一行：`- 被否原因：`（一句话，写清是哪个约束或已核实事实否掉了它）。

### 4. 推荐必须唯一；无法拍板时明确 blocked

证据足够时，末尾写：

```
推荐：方案 X
起决定作用的那条理由：<一条>
仍然会改变推荐的待定问题：<没有就写「无」>
```

决定性证据缺失且无法通过调查补齐时，改写：

```
暂不推荐：没有足够证据承担选错的返工成本
缺少的决定性证据：<一项或多项>
补齐证据后的下一步：<具体动作>
```

不允许出现「都行」「看情况」「各有优劣，看你」，也不允许为了显得果断而在关键未知上猜测。

### 5. 等用户确认，再落盘

用户确认推荐后才写文档；「暂不推荐」本身不落为已选技术方案，只把需要验证的事项加入 `PLAN.md`。

## 输出：只更新以下相关位置

| 落到哪 | 写什么 |
|---|---|
| `docs/DECISIONS.md` | 追加一条 `### D-xxx（选型）`：选定方案 + 起决定作用的理由 + **被否方案及原因**；编号取现有最大编号加一；若替代旧决策，加 `- 取代：D-xxx` |
| `docs/DESIGN.md` | 「技术栈」节：最终栈及已核实版本（**只此一处，不重复理由**） |
| `docs/PLAN.md` | 若含未验证假设，加进「待办」并标 `(假设)`；没有则不写 |

文件不存在时，只创建本次确实需要更新的文件及最小内容，不借机初始化整套文档。

## 硬禁止

- 需求没定就给方案（应该先问）
- 超过 3 套方案，或虚构没有实际可行性的方案凑数
- 推荐用户已经排除的东西
- 有成熟库却自己写（判据：需求对得上、有测试、有人维护）
- 来路不明的包：优先知名公司/基金会/大团队维护、用的人多的
- 记忆里的价格、额度、地区可用性
- 同时推荐两个结论，或把证据不足伪装成确定结论

## 反模式

- 把「选型」做成「技术科普」（用户要的是选哪个，不是框架历史）
- 方案只写优点不写「你得自己管什么」
- 三个方案其实是一个方案（换汤不换药）
- 落盘时把理由抄进 `DESIGN.md`（两处会漂移，理由只留在 `DECISIONS.md`）
