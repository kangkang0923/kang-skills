# 选型问询清单

用法：逐条比对 `docs/REQUIREMENTS.md` 与本次对话，**缺的才问**。条件触发项在条件不成立时整条跳过；本机环境等可调查事实由 AI 自查，不问用户。

顺序 = 依赖顺序：先问杠杆高的（答案会否掉更多方案），不问最重要的。必答项按 1→6 问；每轮最多 5 条，且同轮问题之间不得有先后依赖。条件是否命中依赖未答问题时，留到下一轮。

## 必答 6 条

| # | 问什么 | 为什么要问（答案会怎么改变选型） |
|---|---|---|
| 1 | **平台与运行位置**：桌面（Win10/11、macOS）/ 安卓 / 网页 / 本地脚本；跑在本机还是服务器 | 直接决定技术栈候选集。桌面常驻工具和网页服务没有任何共同候选 |
| 2 | **谁长期维护、他实际会什么**：问经历（部署过网站？写过 C#？管过数据库？用过环境变量？），不问自评「熟不熟」 | 决定「能不能交付」。会 C# 的人维护一个 C# 工具的成本，远低于他不会的 Go |
| 3 | **现成环境**：已装 JDK / Android SDK / .NET / Node / 编译器？能不能装新的？ | 避免为一件小事装一整套工具链；也避免推荐本机根本跑不起来的东西 |
| 4 | **数据**：存哪（本地文件 / 数据库 / 云端）；要不要账号、同步、多人协作；要不要联网 | 决定后端存不存在。「不需要联网」能直接砍掉一半方案 |
| 5 | **硬约束**：指定语言或服务、必须离线、体积上限、合规要求、只能用某个版本 | 用户不会主动说，但会一票否决。不问就会白做一套 |
| 6 | **失败代价**：玩具 / 自用 / 给别人用 / 要上架分发 | 决定该多保守。上架=签名、隐私政策、兼容性；玩具=能跑就行 |

## 条件触发 6 条

| # | 触发条件 | 问什么 | 为什么（真实代价来源） |
|---|---|---|---|
| C1 | 要交给别人用 | 交付形态：单文件绿色版 / 安装包 / 应用商店；要不要签名；版本号怎么管 | 决定打包与分发工具链，也决定升级方式（自动更新 vs 手动替换） |
| C2 | 目标平台有版本差异 | **最低**目标环境：Win10 还是 11、Android minSdk、.NET Framework 还是 .NET 8、Node 版本 | 决定能用哪些 API。Win10 托盘没有分隔符 API、targetSdk 35 强制边到边，这类限制事后补不了 |
| C3 | 涉及系统集成、硬件、或需要真机 | 能不能实机验证？不能的话要内建什么（`--selftest` / dryRun 演练 / 日志文件） | 沙箱验不了的场景必须提前设计可验证性，否则只能靠运气上线 |
| C4 | 要写配置文件或落数据 | 要不要版本化与迁移？写坏了怎么恢复？ | 配置格式一旦发布就改不动；版本字段和原子写要一开始就有 |
| C5 | 用第三方代码、反编译产物、素材，或要上架 | 许可证是什么？能不能随程序分发？要不要隐私政策？ | 授权问题在发布前才发现等于返工；反编译/汉化类项目尤其容易踩 |
| C6 | 后台常驻、开机自启、或移动端 | 内存/电池/启动时间有要求吗？被系统杀掉怎么办？ | 常驻进程的资源与保活策略会倒推技术选型（原生 vs 脚本、前台服务 vs 无障碍） |

## 问完后的自检

- [ ] 每条必答都有明确答案，没有「大概」「应该」
- [ ] 条件触发的项：命中的都问了，未命中的能说出为什么没命中
- [ ] 方案数 1~3 且都实际可行，不为凑数虚构方案；第一套是最简单、用户管得过来的
- [ ] 每套都写了「你得自己管什么」
- [ ] 落选方案都有「被否原因」，且指向具体约束
- [ ] 价格/额度/可用性：有链接+日期，或标了「需你核实」
- [ ] 结论唯一
