## 两条知识纪律（硬约束）

**帕鲁侧：委托人晕 3D 从未玩过帕鲁（D-009）。**

- 上述 6 份文档是唯一事实来源；`references/palworld-quick.md` 只是**机制索引**（提醒有哪些机制、玩家目标是什么），不是事实来源。
- **冲突裁决顺序**：数据表（逐只数值）＞ 材料/料理/设施清单（各自领域，设施等级取科技树口径）＞ 玩法清单（机制总纲）＞ 本 skill 索引。
- 三份清单（材料/料理/设施）末尾都有「勘误建议（对《帕鲁玩法清单》）」小节。**2026-10-26 这批勘误已回写进玩法清单**（§0 有修订记录）；若日后发现新勘误，按清单口径走并把「主文档需同步」记进 `PLAN.md`，不私自在设计结论里沿用旧句。
- 六份文档都带「数据盲区自查」：引用前先看盲区节，别把「未核实」当结论。
- 两处都没有的必须检索，附来源与日期，AI 自审后才可交给用户；**不许凭训练记忆写帕鲁数值或规则**。
- 中文术语一律用官方简中（材料/料理清单已对校 op.gg 官方库）：帕鲁矿**碎块**、**汪汪币**、六棱晶锭、烈阳金属。文档自己标注「社区译名」的（多数帕鲁名、设施名）沿用即可，但要在产出里标明口径。

**堆叠大陆侧：引擎能力以反编译为准。**

- 「引擎做得到/做不到」必须查：`stacklands-mod-common/decompiled/GameScripts/`、`stacklands-mod-common/docs/堆叠大陆Mod开发知识.md`（§五合成、§六坑清单、§八原版机制速查）、`stacklands-palworld/docs/Spike-技术前置分析.md`。
- 查不到 = 未核实：明说「未核实」，需要时进 PLAN.md 待验证，不许拍脑袋断言可行/不可行。
- 玩法语言层（叠放、开包这类玩家可感知交互）可以与用户直接讨论——用户玩堆叠大陆。

## 设计三问与映射四分法

任何机制设计，按顺序过三问，**顺序不许倒**：

1. **玩家目标**：这机制在帕鲁里给玩家的乐趣/目的是什么？（查玩法清单，别猜）
2. **宿主语言**：堆叠大陆的原生交互里，达成同一目标最接近的表达是什么？（读 `references/stacklands-language.md`；引擎边界按上节纪律核实）
3. **差距处置**：帕鲁形式与宿主表达差多远 → 四分法落点。

**映射四分法**：

| 落点 | 判据 | 例子 |
|---|---|---|
| 照搬 | 帕鲁形式能 1:1 翻译成卡牌语言，无结构冲突 | 属性克制 9 系 → 战斗伤害乘区 |
| 适配 | 保留玩家目标，改形式适应卡牌语言 | 捕捉概率 → 血量/球等级掷骰结算 |
| 替代 | 堆叠大陆原生机制直接达成同一玩家目标 | 帕鲁科技树 → 开卡包掉蓝图/想法解锁 |
| 砍 | 玩家目标价值 < 实现成本 | 竞技场 PvP（D-012） |

**内容照搬，交互归宿主**：内容层（帕鲁/物品/配方/数值/掉落）默认尽量照搬帕鲁——材料、料理、设施三层现在都有逐项参考文档，能查就别简化；交互层（输入方式/操作节奏/界面形态）默认优先堆叠大陆原生表达。两层打架时回到第一问（玩家目标），由用户拍板。

**重开旧决策必须显式**：设计若与既有 D-xxx 冲突（如 D-011 放置式劳作、D-004 经济隔离、D-015 v1 简化口径），不得静默绕开或顺手改——明说「这会重开 D-0xx」，走完整讨论，落盘时新决策写 `- 取代：D-xxx`。

## 讨论节奏（沿用 kang-grill 纪律）

- 决策归用户：目标、偏好、取舍必须问，给选项与建议但不替选。
- 依赖链一问一答；同层独立小问可并问，一轮 ≤5 条；每条带建议。
- 沿决策树走，杠杆高的先问；被否分支明确剪枝并记录。
- 问题固定格式（不依赖 kang-grill 已加载）：

  ```
  ❓ Q1｜问题标题
  问题正文，需要时给 A/B/C 选项，选项具体、可直接选。
  ➡️ 建议：推荐哪个 + 一句话理由。
  ```

- 每轮收尾三行：已决 / 未决 / 下一步。

## 设计查漏检查表

查漏模式全表过一遍；单个新设计收尾至少过 A/B/C/E。展开与通过判据见 `references/checklists.md`：

- **A 宿主融合**（首要）：有没有更原生的等价表达？是不是平行发明了一套？
- **B 循环串联**：产出谁消耗？动力怎么推回下一环？
- **C 经济闭环**：source/sink 算账（资源/金币/帕鲁三条线）
- **D 进度曲线**：落在旅程哪段？解锁门槛？毕业点？
- **E 交互一致性**：与已定决策相容？冲突则显式重开
- **F 认知负担**：没玩过帕鲁的看得懂？玩过的预期不落空？
- **G 边界失败态**：缺料/满仓/死亡/跨岛/月末时的行为

## 设计审查（设计债）

对照「设计意图 vs 实现现状」：

1. 逐机制列：设计意图（出处 D-xxx / 设计文档节）→ 实现现状（代码/文档证据）→ 差距
2. 差距分型：**偏差**（做歪了）/ **缺口**（没做）/ **占位**（数值或表现待调）
3. 产出设计债清单 `docs/DESIGN-DEBT.md`，条目格式：

```
### SD-xxx <机制名>
- 意图：<出处>｜现状：<证据>｜差距分型：偏差/缺口/占位
- 建议动作：重新设计 / 调数值 / 补设计文档 / 接受现状
- 优先级：高/中/低
```

4. 每条的建议动作经用户确认后才转进 `PLAN.md` 待办；清单本身覆盖式更新。

## 反模式

- 把帕鲁的交互形态当权威硬塞进卡牌语言（自主寻活界面、实时操作）；反向偷懒也不许——凡帕鲁机制一律「砍」或一律「开包化」
- 凭记忆写帕鲁数值/规则；凭直觉断言引擎能力；把「未核实」说成结论
- 只查玩法清单就下结论（材料/料理/设施三层的细节它没有）；或反过来把设施清单的纯帕鲁事实当已设计内容
- 不读 DECISIONS 就发问，重复问已拍板事项；发现与已定决策冲突却静默绕开
- 只谈形式不谈玩家目标；经济只加产出不加回收
- 一场讨论吃下所有机制——杠杆高的先，其余记未决
